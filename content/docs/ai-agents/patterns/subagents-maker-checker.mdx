## In 3 lines

- **What it is:** A sub-agent is a helper agent that a main agent starts for one job. It works in its own fresh memory and hands back a short result. Maker/checker is a way to use sub-agents: one agent makes the work, and a different agent checks it.
- **Why it matters:** Agents tend to praise their own work. A separate checker, with fresh eyes and a strict brief (its written instructions), catches more of the mistakes the maker misses.
- **Example:** A writing agent drafts a lesson. A reviewer sub-agent sees only the draft and its sources, and lists every claim the sources don't back up.

## Think of it like…

<Analogy>
Think of a bank. One clerk types in a large payment, and a second clerk must approve it before the money moves. Banks call this "maker-checker", also known as the four-eyes principle. Splitting the duties between two people means no single person can push a mistake through alone.

**Where the comparison breaks:** Two bank clerks are different people. Two AI agents may run on the same model, so the checker may miss the same things the maker misses unless you brief it differently.
</Analogy>

## Real-world example

A small marketing team uses an agent to write product pages for an online shoe store. At first, one agent writes a page and then asks itself, "Is this correct?" It almost always says yes, even when a shoe's price or size range is wrong.

So they split the job. The **maker** agent writes the page. Then a **checker** sub-agent gets only the finished page and the product data sheet. Its brief says: "List every fact that does not match the sheet. Do not fix anything." The maker fixes what the checker lists, and the checker looks again. Wrong facts now get caught before a human sees the page.

This learning site works the same way. One agent writes each lesson. A fresh reviewer sub-agent checks it before a pull request, a request to add the change, goes to the owner.

## How it works

First, some terms. A **model** is the AI system that reads text and writes a reply, and a **model call** is one request to it. A **context window** is the text a model can see at once, its short-term memory. An **orchestrator** is the main agent that plans the work and hands out pieces of it.

**Part 1: What a sub-agent is.** In Claude Code, the docs describe a sub-agent this way:

1. It runs in **its own context window**, with its own instructions, called a system prompt, and its own allowed tools.
2. By default, it does **not** see the main conversation. It gets its instructions, a few details about its setup, and the task message the main agent writes for it. (Claude Code also has "forks", sub-agents that do get the whole conversation.)
3. It does the work, then returns **only a summary**. All the messy steps stay out of the main agent's memory.

You can define one as a Markdown file, a plain text file with light formatting, in a project's `.claude/agents/` folder. The settings go in a block between two `---` lines at the top, called frontmatter. Only a `name` and a `description` are required. A `tools` list can limit what it may use. In the example below, `Read` opens files and `Grep` searches them, so this reviewer can look but not change anything.

```markdown title=".claude/agents/fact-checker.md"
---
name: fact-checker
description: Checks a draft against its sources. Never edits files.
tools: Read, Grep
---
You are a strict fact-checker. List each claim the sources do not
support, with the line it is on. Do not fix anything.
```

**Part 2: The maker/checker loop.** Anthropic's guide calls this the evaluator-optimizer workflow. One model call makes an answer, and another judges it and gives feedback, in a loop.

```text
Orchestrator
   │  task
   ▼
Maker ──draft──▶ Checker ──"pass"──▶ done
  ▲                │
  └──── feedback ◀─┘   (repeat until pass or a round limit)
```

The maker drafts, the checker judges, and the loop repeats until the checker passes the work or you hit a set number of rounds.

**Why a separate checker helps.** In a March 2026 post, an Anthropic engineer reports that agents grading their own work "reliably skew positive." Splitting the doer from the judge was a strong fix. The checker was still too lenient at first, though. It would spot real problems, then talk itself into approving the work anyway. Tuning one stand-alone checker to be skeptical was far easier than making the maker doubt itself.

**When it fits.** The guide gives two signs. First, the result clearly gets better when a human explains what to fix. Second, a model can give that same kind of feedback. Clear rules to check against, like "every fact must match a source," make it work best.

**What it costs.** Anthropic's research system uses a main agent plus sub-agents working in parallel, meaning at the same time. It used about 15 times more tokens than a normal chat. **Tokens** are the small chunks of text that models read and write, and you pay per token.

In return, it scored 90.2% higher than a single Claude Opus 4 agent on Anthropic's internal research test. The same post warns that this setup fits poorly when every agent must share the same context. It also fits most coding tasks less well than research.

## Common mistakes

- **Letting the maker check itself** — agents tend to approve their own work. Use a separate checker with a fresh context and a strict brief.
- **Giving the checker the maker's whole history** — it may then reason the same way the maker did and miss the same errors. Give it only the output and what it must check against, like the sources.
- **Vague task messages** — Anthropic found sub-agents with vague briefs repeated each other's work. Give each one a goal, an output format, the tools to use, and clear limits.
- **No stop rule** — maker and checker can loop forever. Set a round limit, and hand the work to a human if it still fails.
- **Adding agents by default** — each one costs tokens and time. Anthropic's guide advises starting with the simplest setup and adding complexity only when it clearly improves results.

## Remember this

<Remember>
- A sub-agent runs in its own fresh context, gets only the task you give it, and returns just a summary.
- Maker/checker: one agent makes, a separate agent with fresh eyes checks, and they loop until pass or a round limit.
- Agents go easy on their own work, so the checker needs a separate context and a strict, skeptical brief.
</Remember>
