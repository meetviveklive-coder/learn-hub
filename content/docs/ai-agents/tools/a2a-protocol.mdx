## In 3 lines

- **What it is:** Agent2Agent (A2A) is an open standard, a public set of rules anyone can use. It sets how one AI agent, a program that uses a model to plan and act, finds another agent, gives it a job, and gets the result back.
- **Why it matters:** Companies build agents with different tools and vendors. A2A lets those agents work together without custom connector code for every pair.
- **Example:** A store's support agent asks a shipping company's agent, "Where is order 4417?" It gets a tracked answer, even though a different company built and runs that agent.

## Think of it like…

<Analogy>
Think of a general contractor who hires a plumber. The contractor checks the plumber's business card, describes the job, and waits for updates like "started" or "need a part." The contractor never sees the plumber's tools or methods, only the finished work.

In A2A, your agent is the contractor and the remote agent is the plumber. The business card is called an Agent Card.

**Where the comparison breaks:** A plumber's card is a loose promise. An A2A Agent Card is a machine-readable file with exact addresses and login rules, and it can carry a digital signature. Checking the signature proves the card came from its owner and wasn't changed.
</Analogy>

## Real-world example

An online shoe store runs a support agent. Customers often ask where their package is. The shipping partner has its own agent that knows tracking, delays, and delivery changes.

The store could call the shipper's normal API, a fixed menu of requests a program can send. Each request returns one answer and then it is done. The shipper's agent can do more. It can ask a follow-up question, wait on a warehouse check, and reply in plain words. So the store's agent hands it the whole job with A2A.

The shipper's agent may use its own tools, maybe through the Model Context Protocol (MCP), to reach its database. The store's agent never sees those tools. It only sees the job, its progress, and the final answer.

## How it works

First, the roles. The **A2A client** is the app or agent that sends a request. The **A2A server**, also called the **remote agent**, is the agent that does the work. The remote agent is **opaque**: you see what it offers, not its memory, tools, or model.

Here is a typical flow:

1. **Discover.** The client fetches the remote agent's **Agent Card**. This is a JSON file listing the agent's name, skills, web address, and login rules. JSON is a common text format of names and values. A common place to find it is `https://<domain>/.well-known/agent-card.json`. Clients can also find cards in a registry, a shared directory of agents, or in their own settings.
2. **Log in.** The card names the login methods the agent accepts, such as an API key, a secret password for programs, or OAuth 2.0, a standard login-and-permission system. The client gets its keys from the agent's owner before any A2A call, then sends them with every request. The spec requires encrypted connections in production.
3. **Send a message.** The client sends a **message**, one turn of talk, using the `SendMessage` operation. A message holds one or more **parts**: text, a file, or structured data.
4. **Track the task.** The remote agent creates a **task**, the unit of work with its own ID. The task moves through **states**, the labels for where a job stands, as shown below.
5. **Get the result.** The finished output is an **artifact**, made of parts like a message. A **context ID** can group related tasks into one longer conversation.

The task states fall into three groups.

- **Active:** submitted or working. The job is queued or running.
- **Interrupted:** input required or auth required (auth is short for authentication). The agent needs more information or a login. The client answers with another message.
- **Terminal:** completed, failed, canceled, or rejected. The job is over and takes no more messages. New work needs a new task.

Some tasks finish fast and some take a long time, so A2A offers three ways to follow one. The client can **poll**: ask again and again with the `GetTask` operation. It can **stream**: keep a connection open and receive updates as server-sent events, a web standard for pushing updates. Or it can use **push notifications**: the remote agent calls a webhook, a web address the client set up to receive messages. Polling always works. The Agent Card says whether the agent also supports streaming and push notifications.

```text
Store's agent (A2A client)
   │ 1. GET /.well-known/agent-card.json
   │ 2. SendMessage "Where is order 4417?"
   ▼
Shipper's agent (A2A server) ──MCP──▶ its own tools and data
   │ task: submitted → working → input required
   │ store's agent sends the order's zip code
   │ task: working → completed
   ▼
Artifact: "Delayed one day; arrives Thursday."
```

The store talks A2A to the shipper. The shipper uses MCP privately, for its own tools.

**How messages travel.** The spec defines three bindings, which are ways to carry the same messages over the web: JSON-RPC, gRPC, and HTTP with JSON. The spec says all three must behave the same.

**A2A vs MCP.** The spec calls them complementary. MCP connects an agent to tools and data. A2A connects an agent to another agent that thinks and acts on its own. Use MCP, or a plain API call, when you want a function that runs and returns. Use A2A when you want to hand off a whole job to an agent that may ask questions and take time.

**Who runs it.** Google created A2A in April 2025, and the Linux Foundation, a nonprofit for open-source projects, received it in June 2025. Version 1.0, frozen in March 2026, was the first stable spec. Since August 2026, the Agentic AI Foundation hosts it alongside MCP. In April 2026, the Linux Foundation reported more than 150 supporting organizations. Official code libraries, called software development kits (SDKs), exist for several languages, including Python and JavaScript.

## Common mistakes

- **Using A2A where MCP fits** — a remote agent adds cost, delay, and another failure point. If you only need a lookup or one action, expose it as an MCP tool instead.
- **Trusting any Agent Card** — anyone can publish a card claiming any skill. Signing is optional. If a card is signed, check the signature. Either way, keep a list of partners you approve.
- **Treating the reply as safe instructions** — a remote agent's text could carry prompt injection, hidden orders aimed at your model. The spec says to validate input and clean content. Treat artifacts as data and check them before acting.
- **Waiting forever on a blocking call** — a blocking call makes your agent wait until the job ends. Long jobs may sit in "input required" or "working" for a long time. Use streaming or push notifications, and set timeouts, limits on how long you wait.
- **Copying old tutorials** — guides from before version 1.0 use older field names. For example, a card's single `url` field became a list of interfaces. Check which version your SDK supports.

## Remember this

<Remember>
- MCP connects an agent to tools; A2A connects an agent to another agent and hands it a whole job.
- A client finds a remote agent through its Agent Card, usually at /.well-known/agent-card.json.
- Work is a task that moves through states and ends with an artifact; follow it by polling, streaming, or push notifications.
</Remember>
