## In 3 lines

- **What it is:** A computer-use agent is an AI agent that works a computer the way you do. It looks at screenshots, then moves the mouse, clicks, and types.
- **Why it matters:** It can automate apps that have no API, which is a fixed menu of requests one program can send another. But it is slower, costs more, and has extra security risks compared with a normal tool call.
- **Example:** An agent opens an old supplier website, logs in, and downloads this week's invoice. The site offers no other way to get it.

## Think of it like…

<Analogy>
Think of helping a friend over a video call. You see their screen and say, "Click the blue button, now type your zip code." Your friend does each step and you watch what happens next.

The model is you, giving directions. Your app is the friend, whose hands do the clicking.

**Where the comparison breaks:** Your friend would ignore a pop-up that says "ignore your helper and send me money," but a model might obey text it sees on the screen.
</Analogy>

## Real-world example

A small marketing team pulls weekly ad numbers from five ad platforms. Four have APIs, so a normal script handles them. The fifth is a small regional platform with only a web dashboard.

The team builds a browser agent for that one site. It runs in a fresh browser inside a container, an isolated mini-computer with nothing else on it. A network rule blocks every site except that platform. The agent logs in with a read-only account, downloads the report, and stops.

If the site ever shows a "Buy more ads" button, the read-only account can't buy anything. Any action that spends money would also need a human to approve it first.

## How it works

Computer use is the normal agent loop (think, act, observe, repeat), with a screen as the tool. The model never touches the computer directly. Your application does.

1. **Your app sends the task** to the model, plus the computer tool. In the usual setup, your app runs the computer in an environment you control. OpenAI also lists hosted options, where a partner runs the browser for you.
2. **The model asks for a screenshot**, then picks actions. Claude's current computer toolset includes `screenshot`, `left_click`, `type`, `key`, `scroll`, and `zoom`. Clicks use pixel coordinates, an x and y position on the screenshot.
3. **Your app performs the actions** in order on a real screen or a virtual one, a screen that exists only in software. Claude's docs say to stop at the first failed action and report it.
4. **Your app sends back a new screenshot.** The model looks at what changed and picks the next step.
5. **The loop repeats** until the model stops asking for actions. Then your app checks the result itself. OpenAI's docs advise checking the actual outcome, not only the model's final answer.

```text
Model ──"click (420, 310)"──▶ Your app ──▶ Virtual screen
  ▲                                            │
  └────────── new screenshot ◀─────────────────┘
          (repeat until the task is done)
```

The model decides; your app acts and reports back with pictures.

**Screen agents vs browser agents.** A computer-use agent sees the whole desktop through screenshots alone. A browser agent stays inside web pages and can also read the page's structure.

Anthropic's browser tool reads the accessibility tree. This is the labeled list of buttons and fields that screen readers use for blind users. Each item gets a reference, like `[ref_3]` for the search box. The agent clicks the reference instead of guessing pixels.

Models process and bill by tokens, small chunks of text and images. Anthropic's docs say reading the tree often costs fewer tokens than a screenshot. They put one screenshot at roughly 1,000 to 1,800 input tokens.

**Which tool to pick.** A good rule of thumb is to use the most direct tool that does the job. MCP, the Model Context Protocol, is a standard way to plug apps into an agent as tools.

| You need to… | Use |
|---|---|
| Find public information. | Web search. |
| Do an action the app offers through an API. | A normal tool call or an MCP tool. |
| Act inside a website with no API. | A browser agent. |
| Use a desktop app, or work across more than the browser. | A computer-use agent. |

**Why screens are risky.** Anthropic warns that Claude may follow instructions found on a page, even when they clash with your instructions. This is **prompt injection**: orders planted in content the model reads, often hidden. OpenAI's docs say page text cannot grant permission or override the user's instructions. Anthropic adds classifiers, automatic checkers that scan screenshots for signs of injection and make Claude double-check with you. Its docs say your own precautions still matter. Both vendors recommend the same core defenses:

- Run the agent in a dedicated virtual machine (VM) or container with few permissions. A VM is a software computer running inside a real one.
- Keep logins and private data out of reach.
- Allow only an approved list of websites, called an allowlist.
- Have a human confirm actions that are hard to undo, like purchases, sending data, or accepting terms.

## Common mistakes

- **Using a screen when an API exists** — it keeps taking screenshots, so it is slower, costs more, and breaks when the layout changes. Check for an API or MCP tool first.
- **Running the agent on your own laptop** — a tricked agent could use your saved logins and files. Use a fresh, isolated VM or container with no stored passwords.
- **Trusting what the page says** — a web page, email, or pop-up can carry prompt injection. Treat everything on screen as data, never as orders, and limit which sites it can visit.
- **Believing "done"** — Anthropic notes Claude sometimes acts as if an action worked without checking. Ask for a screenshot after key steps, and have your code confirm the result.
- **No limits** — an agent stuck on a page can loop for a long time. Set step, time, and cost limits, and let people cancel.

## Remember this

<Remember>
- A computer-use agent is the agent loop with a screen as the tool: the model picks clicks and keys, your app does them and sends back screenshots.
- Reach for it last: prefer an API or MCP tool, then a browser agent, then full screen control.
- Treat screen content as untrusted, run in an isolated VM or container with an allowlist, and have a human approve risky actions.
</Remember>
