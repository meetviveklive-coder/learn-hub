## In 3 lines

- **What it is:** Treating every prompt edit and model change as a software release: versioned, tested, rolled out slowly and easy to undo.
- **Why it matters:** AI output can get worse without any error message, so a small change can quietly break answers for thousands of users in **production** (the live app real people use).
- **Example:** A team tests a new prompt on 200 saved questions, sends it to 5% of users first, and switches back in one click when complaints rise.

## Think of it like…

<Analogy>
Think of a restaurant changing its secret sauce. A careful chef writes down each recipe version, tastes the new one against the old, and serves it at one table before the whole room. If diners frown, the old recipe is still on the shelf.

**Where the comparison breaks:** A cook decides when the recipe changes, but an AI vendor can retire your model on its own schedule, so some changes are forced on you.
</Analogy>

## Real-world example

An online shoe store runs a support assistant. A developer tweaks the **prompt**, the written instructions sent to the model, to make replies friendlier. It looks fine on three test chats, so it goes live for everyone.

Two days later, refund requests jump. The friendlier prompt also made the assistant promise refunds it had no right to give. Nobody can say exactly what changed, because the old prompt was never saved.

The architect fixes the process, not just the prompt. Prompts now live in version control with the code. Every change must pass a saved test set first. New versions reach a small slice of users before everyone, and the previous version stays one switch away.

## How it works

Four things can change an AI app's behavior: the prompt, the model, the tools and data it uses, and the provider's own systems. A safe release process covers each one, so version tool definitions and data sources the same way you version prompts.

### 1. Version and pin everything

- **Prompts:** store them in **version control** (a system like Git that records every change and who made it). Give each release a version number and log which version answered each request.
- **Models:** a **model ID** is the exact model name your code sends with each request. A **snapshot** is a frozen copy of a model at one point in time. **Pin** a fixed ID instead of a moving name. For some older Claude models, Anthropic offers **aliases**, short names that point to the newest dated snapshot of that version; for 4.6 and later, the short ID is itself fixed. Its docs say the model behind a given ID stays constant for that ID's lifetime, and updates ship under new IDs.
- **Watch the edges:** the same docs warn that systems around the model, like the request router, safety filters and sampling logic, can still change and occasionally cause small differences. So pinning reduces surprises; it doesn't remove them.

### 2. Test before release (regression evals)

A **regression** is something that used to work and now doesn't. An **eval** (short for evaluation) is a scored test. A **regression eval** reruns a fixed set of saved test cases against the new version and compares scores with the old one. Include past failures, like the refund promise, so they can never sneak back.

### 3. Roll out slowly (canary)

Google's SRE Workbook calls a **canary** a partial, time-limited deployment of a change, plus checking how it does. **SRE** stands for Site Reliability Engineering, a way of running reliable services that started at Google. A small slice of users or servers, the canary, gets the new version. Everyone else, the **control** group, keeps the old one, and you compare the two.

The workbook stresses splitting measured numbers, like error rate, by group. Its example: a 20% error rate on a 5% canary shows up as only about 1% overall. It also describes **traffic teeing**: copying real user requests to the new version and throwing its answers away, so users never see them.

### 4. Make rollback cheap

**Rollback** means switching back to the last good version. If prompt and model versions are just settings, rollback is a settings change, not an emergency rebuild. The workbook says a failing canary should be paused and rolled back, or escalated to a human.

### 5. Plan for forced changes (deprecation)

Providers retire old models. In Anthropic's terms, **deprecated** means still working but scheduled for removal, and **retired** means requests fail. OpenAI calls that final stage **shutdown**.

- **Anthropic:** at least 60 days' notice to active users before retiring a publicly released model. Partner clouds like Amazon Bedrock set their own dates.
- **OpenAI:** at least 6 months for generally available (fully launched) models. Preview models, early test versions, may get much shorter notice, such as 2 weeks.
- **Both:** email active users and list dates on a docs page.

Both advise testing the replacement well before the cutoff. Treat that migration as a normal release: pin, eval, canary, rollback.

```text
change prompt/model ─→ regression eval ─fail→ fix
                              │ pass
                              ▼
                    canary (small slice) ─worse→ roll back
                              │ same or better
                              ▼
                       full rollout, keep old version ready
```

## Common mistakes

- **Editing prompts live in a dashboard** — no history means no way to know what broke or to undo it. Keep prompts in version control and log the version per request.
- **Using a moving model name in production** — the model can change under you without a code change. Pin a specific ID and upgrade on purpose.
- **Testing on a handful of chats** — three good examples prove little. Keep a saved test set that grows with every bug you find.
- **Watching only the overall numbers** — a canary problem can hide inside averages. Compare canary and control side by side.
- **Ignoring deprecation emails** — a retired model makes requests fail, and preview models may get only weeks of notice. Track retirement dates and start migrations early.

## Remember this

<Remember>
- A prompt edit or model change is a release, so version it, test it and keep the old one ready.
- Pin specific model IDs and rerun a saved regression test set before every change.
- Roll out to a small canary group first, compare it with the control group, and roll back fast if it is worse.
</Remember>
